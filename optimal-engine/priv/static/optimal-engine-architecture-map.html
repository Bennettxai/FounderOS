How To Read This Map

This page explains the mechanics of Optimal Engine: how a human-defined workspace becomes backend state, how data moves through source evidence and memory, how humans and agents retrieve context, and how generated markdown, HTML, app views, and agent actions stay tied to the same governed runtime.

mechanical view

Interface Side

Markdown, HTML, app pages, CLI, API, reports, and agents are control surfaces. They let the human or AI inspect, ask, edit, act, and export.

Backend Side

The runtime owns workspaces, Nodes, source evidence, signals, claims, facts, memory, retrieval, workflow, skills, permissions, and audit.

Projection Rule

Files and pages are generated views or editable surfaces. They are not separate truth unless re-ingested as sources or accepted topology changes.

Build Rule

Each gate must prove a full loop: human action, agent-readable interface, stored record, retrieval or export output, and audit or validation.

Clean Mental Model

Optimal Engine is the whole operating engine. Workspace Topology defines the human/business world, Memory Core preserves source-backed truth, and Retrieval, Active Memory Pools, Skills, Tools, Models, and Exports make that knowledge usable by humans and AI agents.

Backend Runtime Mechanics

The backend is not one giant store module. It is one physical persistence substrate with layer-owned lifecycles. Interfaces send commands into lifecycle services; lifecycle services write governed objects; projections are generated from those objects; agents and humans read through retrieval and policy gates.

backend flow

Command Path

Human, agent, connector, or file edit submits an intent. The engine decides whether that intent is topology setup, source intake, retrieval, tool execution, export, or promotion.

Lifecycle Services

Each layer owns meaning: Workspace / Topology owns Nodes, Memory Core owns sources and truth, Retrieval owns context packages, Workflow owns reusable procedure.

Physical Storage

One database can hold many table groups, but write ownership is separated. Store executes persistence; domain layers decide what can be written.

Generated Surfaces

Markdown, HTML, app views, dashboards, reports, and agent prompts are projections. They read from engine objects and carry enough metadata to be traced back.

Storage Contract

This is where the system prevents itself from becoming bullshit. Every stored thing must be classified as durable truth, task-local state, projection, execution record, policy record, or cache. The same physical database can hold all of them, but they do not mean the same thing.

storage truth map

Canonical Truth

Objects the engine must preserve as governed state: workspaces, Nodes, source packages, Claims, Facts, Memory Objects, relationships, workflows, skills, policies, and audit.

Task State

Objects that are durable but scoped to work in progress: Active Memory Pools, observations, pending Claims, loaded context, tool/model runs, and execution records.

Projections

Generated or compatibility views: markdown files, HTML pages, app cards, context rows, FTS rows, vectors, summaries, and Context Packages. Useful, but not raw truth.

Data Anatomy And Multimodality

This is the shape of every thing that enters the engine. Optimal Engine cannot treat everything as text chunks. It must preserve native evidence, type the payload, process each modality correctly, and only then derive Signals, Claims, Facts, Memories, Context Packages, Workflows, and Skills.

data contract

Source Package

The preserved evidence container: source URI, source time, received time, content hash, trust label, retention, security labels, raw text or archive URI, and metadata.

Data Architecture

The schema for a payload: fields, modality, shape, required flags, granularity, retention, and processor bindings. This is how the engine knows what kind of data it is handling.

Processor Outputs

Parsed text, OCR, transcripts, captions, scene cuts, chunks, embeddings, table fields, graph edges, and time-series features. These are rebuildable from the source.

Architecture.Field defines modalities. Built-in Data Architectures cover text, image, audio, structured records, time series, code, and multimodal media. Chunks carry modality and asset references. The embedder dispatches text, image, audio, and video fallback paths.

Still Needed

Binary raw artifact storage, source package support beyond raw text, processor-run lineage tied into Derivation Ledger, native source spans for non-text, and multimodal Context Packages that cite frames, regions, rows, cells, and time offsets.

Reality Audit

This is the gap between the architecture and the current codebase. The model is pointed in the right direction, but these are the places where current implementation can still betray the architecture.

current risk

Biggest Structural Gap

The schema has nodes.workspace_id, but the current Node interface is still tenant/slug-first. Workspace ownership exists as a column, not yet as the enforced topology lifecycle.

Biggest Intake Gap

The Source Package is built early but persisted after classification, file write, and Context indexing. Source evidence must be guaranteed before interpretation.

Biggest Runtime Gap

The system has first lifecycle services for Claims, Facts, Memory Objects, Context Packages, Active Memory Pools, draft Skill Packages, and governed model/tool run records. The remaining gap is deeper policy, review, graph/hybrid retrieval, real dispatcher execution, recovery, and benchmark proof.

Reality Finding Why It Matters Correction
Node ownership is partly workspace-enforced. Workspace-scoped Nodes, Node Types, memberships, and relationships exist. API workspace creation now routes through the topology lifecycle; other surfaces still need the same enforcement. Make CLI/app/import workspace creation call the topology service and add tests proving seeded Node Types and workspace-scoped relationships from every surface.
Source evidence is not a hard first commit. Rejected or failed intake can lose source evidence; generated files or Context rows can exist without guaranteed provenance. Persist Source Package before classification and record rejected/quarantined intake attempts.
Context still carries too much meaning. Old code still treats contexts as central. That can keep pulling truth back into a compatibility/search projection. Rename mentally and in docs as compatibility Context; build RetrievalPackage and ContextPackage services.
Truth lifecycle has a first deterministic slice, not full policy. KnowledgeLifecycle can create Claim, Fact, Memory Object, support edges, and ledger entries, but review queues, scoring policy, contradiction handling, and supersession are still shallow. Add policy/review workflows, richer extraction, temporal narrowing, contradiction/supersession behavior, and calibration.
Retrieval is useful but not fully governed recall. Memory Core recall now excludes stale, contradicted, and superseded current-memory candidates, but the broader Search/RAG path still needs full pre-expansion authorization, graph/vector planning, redaction links, and audit IDs. Build full RetrievalPlanner, graph/FTS/vector expansion under authorization, redacted object links, and retrieval audit IDs.
Exports need hard export records. Markdown/HTML/app views can drift from database state or become a second truth. Add export records with object links, object versions, output path, hash, policy, and rebuild metadata.
Active Memory Pools have a first runtime slice, not a full runtime. Agent work can now be captured as loaded context, observations, and pending Claims, but tool/model execution and membership policy are still shallow. Build stricter membership enforcement, refresh/invalidation, pool audit IDs, and tool/model run integration.
Tool/model governance has records, output checks, and run audit links, but not full dispatch. Registered calls can be permission-checked, input-checked, output-checked, recorded, linked to audit metadata, and valid completed output can create an observation. Real external tool/model execution is not yet forced through the governance layer. Wire connectors, model providers, and MCP/API tool calls through the governance service; add richer schema validation, persistent audit lookup, and source conversion for failed executions.

Nearby system patterns validate parts of the direction, but none should define the whole engine. Treat them as design inputs: learn from what they make concrete, then keep Optimal Engine's workspace/node/runtime architecture sharper.

patterns

Shared Team Memory

A shared memory product for people and agents. The lesson is interface clarity: work-tool ingestion, team memory, living briefs, and MCP recall wherever people already work.

CLI/MCP Brain

The closest reference: CLI/MCP brain, graph retrieval, answer synthesis, schema packs, skill packs, background enrichment, and public evals. The lesson is operational proof.

Markdown Wiki Runtime

A low-ops Markdown wiki with SQLite, a page tree, backlinks, broken-link status, live editing, optimistic locking, revisions, link refactor, import, and simple roles. The lesson is export/interface quality.

How People Use It

The user experience is markdown-operable, database-backed, and agent-controlled. A person can manage companies, project Nodes, people, rhythm, decisions, workflows, and outputs through files, an app, a CLI, or an agent, while Optimal Engine keeps the canonical state governed underneath.

Primary example

Markdown Control

Humans can inspect and edit workspace files directly: node context, current signal, rhythm, playbooks, deliverables, reports, and package outputs.

Runtime State

The database stores governed identity, sources, signals, claims, facts, memories, relationships, workflows, skills, permissions, audit, indexes, and export records.

Interface Surfaces

Apps, dashboards, HTML pages, CLIs, APIs, and agents all operate the same objects instead of creating separate versions of the workspace.

Node Ontology

A Node is the governed topology object that gives work a place. It can export to a folder, but the folder is not the source of truth. The Node owns identity, relationships, state, focus, context, decisions, tracking, and lifecycle.

Workspace topology

Identity

  • name, type, purpose
  • owner and status
  • tenant and workspace scope

Relationships

  • parent and child nodes
  • dependencies and blockers
  • people, systems, workflows

State

  • health, progress, metrics
  • risks and blockers
  • review cadence

Context

  • sources, signals, memories
  • decisions and open questions
  • context packages and exports

Universal Modeling Rule

Do not create a separate hierarchy for every domain concept. Workspace is the container. Node is the universal organized unit. Node Type says what kind of thing it is. Relationships say how Nodes connect. Profiles are added only when a type needs stable, queryable fields.

Devil's Advocate

These are the ways this architecture can go wrong if we build it carelessly. Each risk has to become a guardrail in the code, docs, and product behavior.

Pressure test

Node Becomes A Junk Drawer

If every concept is a Node with loose metadata, the model can become vague and impossible to query. Guardrail: keep universal Node fields small, use typed relationships, and add profiles only when stable fields earn schema.

Markdown And Database Drift

If files and runtime state both pretend to be truth, they will diverge. Guardrail: every export needs an export record, every human edit re-enters as a Source Package or governed topology update.

Agent Writes Too Much Truth

If agent observations become Facts automatically, the system will poison itself. Guardrail: tool results and generated text become observations or pending Claims until review or policy promotion accepts them.

Retrieval Looks Smart But Leaks

Search can expose restricted context through summaries, edges, or citations. Guardrail: permissions apply before candidate generation, graph expansion, context assembly, tool calls, and export.

Too Many Interfaces, No Core

HTML pages, dashboards, CLI, agents, and apps can distract from lifecycle correctness. Guardrail: build one end-to-end vertical slice before adding more surfaces.

Workflow Skills Become Prompts

If Skill Packages are just prompt files, they are not governed procedures. Guardrail: each skill needs source links, preconditions, tools, validation checks, exceptions, permissions, and audit.

Question Hard Answer Build Rule
Should every thing be a Node? No. Every durable operating area can start as a Node, but tasks, one-off notes, and throwaway artifacts should attach to Nodes instead of becoming Nodes. Create a Node only when it needs identity, lifecycle, relationships, review, permissions, or durable context.
Should profiles come early? Only for fields the engine must query, validate, govern, or report. Otherwise metadata is fine during discovery. Start with Node + metadata; promote to profile table after repeated field use.
Should markdown be source of truth? It is a control surface and projection. It can become new evidence when edited, but canonical identity and lifecycle live in the engine. Use export manifests, content hashes, source packages, and re-ingestion records.
Should we build the app now? Not before the core write/read lifecycle works. Otherwise the app will encode temporary assumptions. Build UI only around one vertical slice: Node -> Source -> Claim -> Fact -> Context Package -> HTML/export.
Should Active Memory Pools be called workspaces? No. Workspace is the top container. Active Memory Pool is a task-scoped working context inside a Workspace. Use Workspace for the container; Active Memory Pool for sessions/tasks.
Should one database hold all layers? Yes initially, but table ownership cannot be shared casually. One physical store, many lifecycle owners. Store executes writes; domain layers decide meaning.

What Are We Doing First?

The first thing is not the app, not agent automation, and not the full memory lifecycle. The first thing is the Topology And Workspace Surface Foundation: make workspaces and Nodes real governed objects, then prove the human can operate them through markdown or HTML with export records, link health, revisions, and audit.

first gate

The Product Move

Turn a markdown-operable personal/company workspace into a governed operating engine. Markdown remains useful, but the engine owns identity, lifecycle, routing, permissions, memory, retrieval, and audit.

The First Gate

Build Workspace, Node, Node Type, Node Relationship, Node Member, Export Record, Page Tree, Link Health, and Projection Revision. A project is a project Node, not a top-level peer beside Workspace.

The First Proof

Create a workspace, create company/person/project/operation Nodes, link them, export markdown or HTML, verify links/backlinks/drift, then re-ingest an edit as a source or governed topology change.

Layer/Gate Map

A layer is an ownership boundary. A gate is a build proof that crosses layers. A surface is how humans and agents use the engine. A projection is a rebuildable view of governed state.

structure rule

Layer

Owns a lifecycle and decides what a table or object means. Example: Workspace / Topology owns Nodes.

Gate

Proves a working dependency across layers. Example: Topology + Surface proves creation, export, link health, re-ingestion, and audit.

Surface

Lets humans or agents operate the engine. Example: markdown, HTML, CLI, API, app, or tool call.

Projection

A generated view that can be rebuilt from engine state. Example: node markdown, dashboard cards, context snippets, HTML reports.

Dependency Build Sequence

The architecture should not be built around an arbitrary number of phases. It should be built through dependency gates: each gate keeps the meaningful complexity it needs and proves the next part of the engine can safely exist.

dependency gates

Topology + Surface

Build Workspace -> Node -> Node Type -> Relationship -> Export Record -> Page Tree -> Link Health -> Revision. This proves the operating shape and the human surface together.

Evidence Intake

Build Command/Raw Input -> Scope Envelope -> Source Package -> Signal -> route to Node -> compatibility Context row -> Derivation Ledger. This preserves evidence before interpretation.

Truth Lifecycle

Build Claim -> Fact -> Memory Object with temporal state, confidence, precision, and source links. This prevents notes and agent output from becoming truth too early.

Governed Recall

First Retrieval Package -> Context Package path exists with source links, node/task scope, freshness checks, and filtered-object accounting. Next: richer graph/FTS/vector planning, redaction, and package audit IDs.

Agent Work Loop

First Active Memory Pool path exists with loaded context, observations, pending Claims, and governed tool/model run records. Next: membership enforcement, refresh, dispatcher integration, and stronger audit.

Workflow, Skill, Evaluation

First Workflow Trace -> Generalized Workflow -> Procedural Memory -> draft Skill Package path exists. Next: execution policy, validation gates, dashboards, benchmark suites, recovery checks, and MCP smoke tests.

Naming Rules

Use product-native names in public-facing material. Keep the academic/database category language out of product pages unless the page is explicitly technical research.

Use

Optimal Engine, Workspace, Node, Memory Core, Source Package, Claim, Fact, Memory Object, Context Package, Active Memory Pool, Skill Package.

Avoid publicly

External project names, comparison language, and wording that makes one subsystem sound like the whole product. The whole product is Optimal Engine; Memory Core is the governed memory subsystem inside it.
