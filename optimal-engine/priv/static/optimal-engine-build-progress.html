Hosting Reality

Optimal Engine does not require Docker for local development. Docker is already present as a self-hosted packaging and deployment option. The same engine data model should work in both modes.

Docker optional

Local Mode

Run directly from the repo with Elixir/Mix. Data lives on the local filesystem and SQLite database path configured for the engine.

  • ✓No Docker required for local dev.
  • ✓Good for building, testing, indexing local workspaces, and using markdown directly.
  • ✓Current tests run this way.

Docker Self-Hosted Mode

The repo has a compose stack under deploy/. It runs the engine plus desktop/site/docs containers.

  • !deploy/docker-compose.yml starts the engine on port 4200.
  • !deploy/Dockerfile.engine builds an Elixir OTP release.
  • !Persistent state is mounted at /data inside the engine container.

Production Target

Production can be self-hosted with Docker today, but the long-term data layer should be able to move from SQLite to Postgres when the workload needs it.

  • •SQLite is the current built store.
  • •Postgres is the likely production-grade truth store target.
  • •Indexes/caches can remain attached and rebuildable.
Mode How It Runs Where Data Lives Use When
Direct local mix commands and local engine runtime. Configured local root path and SQLite DB path. Development, tests, personal workspace, fast iteration.
Docker local/self-host cd deploy && docker compose up --build Docker volume optimal_data mounted at /data. Running the engine/API/UI stack as a packaged self-hosted system.
Production self-host Compose production overlay with auth and reverse proxy/TLS. Persistent volume today; future Postgres/object storage path when needed. Team/organization deployment where uptime, auth, backup, and recovery matter.
Architecture rule: Docker packages the runtime. It does not define the data model. The data model is owned by the store migrations and lifecycle modules.

How People And Agents Use It

The engine should support multiple surfaces without creating multiple truths. Each surface sends commands or edits into the same lifecycle.

Product rule

Markdown

Direct human-operable workspace. Good for local control, reading, editing, and portable projection.

HTML / App

Navigation, diagrams, dashboards, Node pages, reports, progress views, and visual status.

CLI / API

Fast commands, scripts, integrations, import/export, smoke tests, and app backend access.

Agent / Tool

Task execution through authorized context, active pools, registered tools, observations, and audit.

Surface rule: a file edit, UI event, CLI command, API request, or agent tool call must become either a topology operation, a Source Package, an observation, a projection request, or an audited read.

Link Nodes Typed relationship row with direction, validity, creator, and policy. Prevents relationships from becoming loose markdown links only.
Export surface Markdown or HTML generated from engine state, export record, projection revision. Proves the human can see and operate the workspace.
Check links Backlink and broken-link report stored as link health. Prevents wiki drift and dead references.
Edit projection Built Edit captured as Source Package or topology change request. Prevents markdown from silently bypassing governed state.
Route edit back to Node Built Signal record, route decision, compatibility context/search projection. Connects the old signal/search advantage to the new object lifecycle.
Audit all actions Trace from actor to command/edit to stored records and projection. Lets the system explain how state changed.

Do Not Start With These

These are important, but they depend on the early gates. Starting here would create impressive surfaces over unstable lifecycle state.

Defer

Full App UI

Build small generated views now. Do not build the full app before Node identity, projection records, and source re-entry are working.

Full Agent Autonomy

Agents should not freely mutate topology or truth until tool governance, active pools, and pending-claim review exist.

Skill Runtime

The first draft Skill Package lifecycle exists. Full execution, validation checks, exceptions, rollback, permissions, tool requirements, and runtime policy enforcement still come later.

Workflow Mining

Trace capture from Active Pools exists. Mining repeated cases, clustering variants, exception paths, and review-based generalization still come later.

Public Benchmark Claims

Benchmark pages should wait for repeatable datasets, judge configuration, run logs, and reproducible output records.

Extra Domain Tables

Do not invent a table for every use case yet. Use Node types and custom metadata until a lifecycle proves a separate object is needed.
